# 強化學習（RL）交易員可行性評估

> 結論先講：**現階段 No-Go（不建議實作）**。本文件記錄評估過程與「未來什麼條件下值得重啟」，
> 避免之後重複討論。對照概念：MDP / DQN / PPO / TD Learning。

## 1. 背景與動機

強化學習交易員的想法：把交易建模成**馬可夫決策過程（MDP）**——

- **狀態（State）**：今天的市場特徵（價格、技術指標、籌碼面）
- **動作（Action）**：買入 / 賣出 / 持有（DQN 的離散動作），或目標倉位比例（PPO 的連續動作）
- **獎勵（Reward）**：報酬（扣成本、罰回撤）
- **學習方式**：TD Learning——不用等整段走完才回算，用「明天的預測」修正「今天的預測」

DQN（Deep Q-Network）輸出每個動作的 Q 值（預期總回報）；PPO（Proximal Policy
Optimization）直接學策略本身，適合連續倉位控制（例如「明天持有 42% 多單」）。

聽起來很適合交易。問題出在**資料量**與**過擬合**。

## 2. 資料量現實：日線餵不飽深度 RL

| 項目 | 數字 |
|------|------|
| Alpaca 免費版日線 | 約 250 bars／年／檔 |
| 10 年單一標的 | 約 2,500 個決策點 |
| 100 檔 × 10 年 | 約 250,000 個決策點 |
| DQN 玩 Atari 的訓練量 | 數百萬～數千萬步 |
| PPO 典型訓練量 | 百萬步起跳 |

深度 RL 的神經網路參數動輒數萬～數十萬個，而我們的「真實獨立樣本」只有幾千筆，
且金融時序**非平穩**（2010 年的規律到 2024 年可能失效）、**訊噪比極低**（日報酬
幾乎是雜訊）。網路有足夠容量把雜訊背下來——訓練曲線會很漂亮，實盤會還原成運氣。

## 3. 過擬合風險：直接撞上本專案的 OOS 鐵則

CLAUDE.md 鐵則：「挑冠軍／設門檻一律看樣本外（OOS）」。RL 在這條鐵則下特別吃虧：

- RL 訓練本質是在**同一段歷史上反覆迭代數萬次**，等於對訓練段做了極深度的資料窺探
  （data snooping），比網格搜尋 8 種策略 × 幾十組參數嚴重幾個數量級。
- reward 設計、網路架構、超參數（學習率、折扣因子 γ、探索率 ε…）每調一次，
  都是一次隱性的多重檢定——OOS 驗證要扣的「自由度成本」極高。
- 文獻與實務共識：日線級 RL 交易策略**極少能通過嚴格的 walk-forward 樣本外檢驗**；
  能通過的多半依賴高頻資料或另類資料（本專案都沒有）。

## 4. 與現有 regime + strategy_selector 的比較

本專案 Phase 7 已實作「可解釋版的狀態→動作」：

| 面向 | RL（DQN/PPO） | 現有 regime + selector |
|------|---------------|------------------------|
| 狀態辨識 | 隱含在網路權重裡，不可解讀 | `regime_features.py` + `regime.py`，特徵明確 |
| 狀態→動作 | 黑盒 Q 值／策略網路 | `strategy_selector.py` 對照表，一眼看懂 |
| 倉位控制 | PPO 連續動作 | `sizing.py` 分數凱利（有理論依據、可審計） |
| 樣本需求 | 百萬步級 | 幾百筆 OOS 交易即可統計檢驗 |
| 除錯成本 | 訓練不收斂／reward hacking 難排查 | 每層獨立、`layer_validation.py` 可逐層驗加分 |
| 審計 | 無法解釋單筆決策 | `DecisionLog` 每筆決策留痕 |

換句話說：**RL 想學的東西，我們已用可解釋、低樣本需求的方式拆解實作了**。
RL 的潛在增益是「自動發現人沒想到的狀態—動作對應」，但在日線資料量下，
這個增益大概率被過擬合吃掉。

## 5. 若要做，需要哪些基建（成本盤點）

1. **Gym 環境**：把 `backtest_engine.py` 包成 `gymnasium.Env`——必須維持
   「回測 = 實盤」鐵則（隔日成交、含成本、同資料源），否則 RL 學到的是作弊技巧
   （用當根收盤成交 = 偷看未來，RL 一定會學會利用這個漏洞）。
2. **Reward 設計**：天真的「每日報酬」會學出高槓桿賭徒；要罰回撤、罰換手成本，
   而每改一次 reward 都是重訓 + 重驗的循環。
3. **評估管線**：walk-forward 訓練/驗證切分（訓練 2015-2020 → 驗 2021，滾動前推），
   對接現有 `validation.py`；至少要證明 OOS 加分顯著高於現有 selector 基線。
4. **算力**：CPU 可跑但慢；認真調參需要 GPU 與實驗追蹤（MLflow 之類）。
5. **依賴**：`gymnasium` + `stable-baselines3`（PPO/DQN 現成實作）+ PyTorch。

粗估是一整個 Phase 的工作量，且失敗（過不了 OOS）機率高。

## 6. 結論：No-Go（現階段）＋重啟條件

**不建議現在實作。** 預期投入產出比遠低於既有路線的增量改進
（例如：更多策略進知識庫、meta-labeling 調優、MC 壓力測試常態化）。

未來**同時滿足**以下條件時，值得重新評估：

1. **資料升級**：取得分鐘線（樣本量 ×390）或多標的長歷史，決策點達百萬級。
2. **基線完備**：regime + selector 的 OOS 加分已驗證且穩定，有明確的「RL 要打敗的對手」。
3. **風險基建就緒**：蒙地卡羅壓力測試（`monte_carlo.py`）已常態化，能對 RL 策略
   做破產機率評估，而不是只看回測報酬。
4. **入門路徑**：先做「RL 只調倉位、不選方向」的窄任務（接在現有訊號之後，
   類似 meta-labeling 的定位），樣本需求低、可控性高，而不是端到端全包。
